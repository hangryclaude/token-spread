the "fully deployed" language. The underlying mechanism — Marketplace purchases retiring committed cloud spend — is real; this specific number and date are not.

9. **Volume-tier enterprise negotiation "benchmark" percentages** (e.g. "$1M–$5M commit → 15–25% off," "$5M+ → 25–40%"). A cluster of roughly seven SEO/negotiation-consulting sites publish near-identical, suspiciously precise commit-tier bands with no named source or visible methodology. No provider publishes anything like this. Anchoring a real negotiation on these numbers risks mis-anchoring in either direction — worse than negotiating with no number at all.

10. **Unsourced blogspam waste percentages** ("43% of LLM spend is wasted," "34% from retry storms," "85% of apps have duplicate-call issues"). Traced directly to a single self-promotional post for the author's own monitoring tool — no sample size, no methodology, no citations. Never quote these, even with a caveat attached; the caveat gets dropped downstream and the number survives on its own.

11. **CacheGen marketed as "lossless KV compression."** Repeating this claim without reading past the paper's title is a real, observed error pattern in survey articles — see §4 for the verified mechanism.

12. **Kong AI Semantic Cache cited as open-source prior art.** The actual open-source Kong Gateway repo has no AI-specific caching plugin at all (confirmed via direct grep of the OSS `handler.lua`); the semantic-caching product is Enterprise/Konnect-only, and its cache-key/threshold mechanics are undocumented publicly. Citing "Kong does semantic caching" as OSS prior art is simply wrong.

13. **Structured Outputs "schema caching" presented as a token-cost saving.** The only documented benefit of schema reuse is reduced *first-request latency* from compilation avoidance. Any real token-cost benefit of a stable schema comes from ordinary prompt caching treating the schema as any other cacheable prefix content — a separate mechanism. Don't double-count the two.

14. **OpenAI's `previous_response_id` / server-side conversation state presented as a cost-reduction feature.** OpenAI's own docs state plainly: "even when using `previous_response_id`, all previous input tokens for responses in the chain are billed as input tokens in the API." Statefulness is a convenience feature, not a billing one. Any savings on repeated multi-turn context come entirely from prompt caching matching the resent identical prefix — a mechanism that applies equally if the caller manually resends the history themselves.

15. **`seed` + `system_fingerprint` (OpenAI) presented as a provable determinism/identity primitive.** OpenAI's own docs describe this as "best effort" and explicitly warn outputs can differ even when seed and fingerprint both match. The parameter is also entirely absent from the Responses API — OpenAI's stated forward direction — with no announced replacement.

16. **Batch-invariant inference kernels (Thinking Machines Lab) presented as a cost lever.** This is the one credible, working path to real byte-for-byte determinism, and it is a straight **cost increase** — 2.1x slower unoptimized, ~1.6x slower with an optimized attention kernel — not a saving. Flag as a genuine industry-wide tension: true Tier-A byte-determinism and lower serving cost currently pull in opposite directions, and any pitch claiming both simultaneously from the same mechanism deserves extra scrutiny.

17. **"A one-time cert or benchmark proves identity forever."** Every borrowed methodology found in this sweep — compiler translation validation, Netflix's Kayenta canary analysis, financial parallel-run certification, FDA 510(k) substantial-equivalence review — treats the guarantee as continuously re-earned, never a one-time proof. A stale cert is not evidence about today's traffic, especially given documented provider-side harness drift under an *unchanged* model ID (the Anthropic Mar–Apr 2026 incident, §2.10).

18. **"We ran a t-test and found no significant difference," presented as proof of output equivalence.** Classic statistical malpractice — failing to reject H0 is equally consistent with an underpowered study as with true equivalence. The correct tool for an equivalence claim is TOST against a pre-registered margin, not ordinary null-hypothesis significance testing.

19. **AWS/GCP claimed as running speculative decoding, batch-invariant kernels, or PagedAttention-style KV sharing in their production frontier-model APIs, presented as fact.** No primary-doc source, positive or negative, was found for any of the three major hosted frontier APIs (OpenAI, Anthropic, Google) on this question. Everything found was either research with no confirmed commercial deployment, or confirmed deployment at a *different* provider (Moonshot/Mooncake, Fireworks/FireAttention) that isn't one of the big three. Do not write "Provider X uses technique Y" about any frontier lab without a primary source — none currently exists.

## 6. OPEN QUESTIONS — what nobody has measured, including us

Each item below is tagged "unknown" by at least one adversarially-screened dimension, and each carries the experiment that would settle it, per the brief's own instruction not to default to A when unsure.

1. **Does closing/aborting a streaming connection actually stop a hosted provider from generating (and billing for) further tokens?** Confirmed billed-up-to-abort for Google Vertex (named engineer, official forum); practitioner consensus only for OpenAI; inferred but not confirmed for Anthropic. *Settling experiment:* stream a long completion, hard-close the TCP connection mid-stream (not a graceful end), then query the provider's usage/billing endpoint for that `request_id`.

2. **Does OpenRouter's sticky-routing key (used to route repeat requests to the same upstream provider so *that* provider's own cache can hit) persist for a session's full lifetime, or reset on provider failover?** Docs never state a stickiness TTL. If a duplicate request fails over to a different provider serving nominally the same model (different quantization/implementation), the Tier-A guarantee breaks silently. Reclassified from A to unknown for exactly this reason during merge.

3. **Does Batch/Flex/Priority-tier serving run on identical weights/precision to standard synchronous serving, or route to different hardware/quantization?** No primary doc states parity either way, for any provider. *Settling experiment:* large-N identical-prompt diffs across service tiers at temperature 0, comparing logprobs where available.

4. **Is strict-rejection-sampling speculative decoding (the mathematically distribution-preserving Leviathan/Chen algorithm) actually running in any major hosted frontier API today?** No confirmation either way. Even where it *is* used, one real measurement (arXiv 2606.25097, real vLLM stack) found only **90.66% byte-identity** between spec-decoding and target-only decoding at T=0 — the gap traced to floating-point non-associativity in the verification step, not a flaw in the proof. The proof guarantees the output *distribution* matches in expectation; it does not guarantee a single sampled run is byte-identical. *Settling experiment:* run the same measurement against actual hosted commercial APIs rather than self-hosted vLLM — nobody has published that yet.

5. **Does continuous/dynamic batching — the near-universal production scheduling technique — measurably perturb a single request's output**, because most GPU kernels (RMSNorm, matmul, attention) are not batch-invariant, and identical math returns different floating-point results depending on concurrent batch composition? Thinking Machines Lab's own research demonstrates this is real in principle (1000 T=0 completions → 80 unique outputs before their fix, all-identical after). *Settling experiment:* repeat a fixed prompt at T=0 under a provider's real production load (varying concurrent batch composition) vs. isolated/dedicated capacity, diff outputs.

6. **Does routing through the async Batch API change the load/scheduling regime enough to trigger the same batch-composition-dependent divergence described in #5?** No provider states parity in either direction. *Settling experiment:* pair real-time and batch responses to identical T=0 prompts, measure divergence rate against a real-time-vs-real-time baseline.

7. **Does enabling Zero Data Retention silently disable or degrade prompt-caching discounts (which imply some retention window) on OpenAI or Anthropic?** A real, testable interaction between a procurement-mandated security control and a cost-saving technical lever, never settled by either provider's marketing. *Settling experiment:* toggle ZDR, inspect cache-hit billing behavior on an otherwise-identical request pair.

8. **Does trimming tool/function schema description verbosity change tool-selection or parameter-fill accuracy?** Mechanically, shorter descriptions are certainly fewer tokens — measured 3.58x reduction on a representative schema. But both Anthropic's and OpenAI's own primary docs argue the opposite direction, explicitly recommending verbose, detailed descriptions as the single most important factor in tool performance. No controlled ablation isolating description length alone, holding tool count/names/schemas fixed, was found anywhere — vendor or academic. *Settling experiment:* fix a 5–20 tool library with some near-duplicate-purpose tools, construct three description-length tiers per tool, run each against an ambiguous-selection eval set across two or more model generations, measure selection accuracy **and** token cost together.

9. **Do explicit `cache_control` markers (Anthropic-style) actively hurt Gemini's own implicit caching?** Confirmed as a live engineering-team code comment in one multi-provider SDK: sending Anthropic-shaped markers to Gemini freezes its native implicit cache at that static point and disables it on everything appended afterward — estimated 6–14x higher cost versus doing nothing. No evidence found that Gemini's *output* changes, only its cost, but the internal-state uncertainty is real. Any "provider-agnostic" caching abstraction must special-case Gemini or silently overcharge its users.

10. **Does sub-agent context isolation ever net out ahead on total tokens/dollars for a fixed task**, versus one monolithic agent whose single context grows quadratically over the same total work? Anthropic's own 4x/15x figures compare multi-agent to plain chat, not to an equivalent-total-work single long-running agent — that specific head-to-head has not been run anywhere found in this sweep. *Settling experiment:* same task, same total tool-call volume, two architectures, real token totals logged.

11. **What is the actual current-day production spend-category breakdown** (cache-write / cache-read / uncached-input / output / thinking-token share) across real agent-loop traffic? No provider, harness, or engineering blog publishes this anywhere found across fourteen independent research passes. The single largest, cleanest data gap this product could fill by instrumenting real customer traffic, since no published number exists to compare against.

12. **Does replaying prior-turn reasoning items via OpenAI's `reasoning.context: all_turns` receive the cache-read discount on the next call, or bill as fresh uncached input every time?** OpenAI's docs describe the mechanism (and confirm it changes model input, hence Tier C on the input-identity axis) but not its billing treatment. *Settling experiment:* diff `usage.input_tokens_details.cached_tokens` across two otherwise-identical multi-turn runs, `all_turns` vs. `current_turn`.

13. **Is Anthropic's prompt-cache hash computed over raw pre-parse request bytes, or a post-parse reconstructed prompt?** One fetched example implied pure JSON-envelope whitespace differences (never touching prompt-bound string content) break the cache — architecturally odd given the same doc's own component-level invalidation granularity (a `tool_choice` change invalidates only the messages-cache, not tools/system). Could not be independently verified; no live API key was available to run the decisive test. *Settling experiment:* send two functionally identical requests differing only in envelope whitespace with a `cache_control` breakpoint set, check whether `cache_read_input_tokens` is nonzero on the second call.

14. **Does Anthropic's server re-serialize a tool's `input_schema` canonically before splicing it into the tool-use system prompt, or echo the client's literal key order/whitespace verbatim?** Determines whether tool-schema key order belongs in the safe Tier-B canonicalization set (§2.2). *Settling experiment:* `count_tokens` with permuted key order, not run in this sweep for lack of API access.

15. **Root cause of a reported $1,771-in-4-hours Claude Code billing anomaly against a $25/month configured limit (~70x overshoot)** — compromised API key/fraud, or an internal retry/loop bug? The public thread doesn't resolve it; material to whether this belongs in a "pure waste" catalogue at all versus a security-incident catalogue.

16. **Is the reported GPT-5.6 "`usage.output_tokens` reported at ~9x actual generation, re-summed once per reasoning item" billing bug real and provider-confirmed, or a single misdiagnosed report?** Only an OpenAI support acknowledgment-of-receipt exists as of the source thread's end — no public confirmation or fix. Do not present the 9x figure as established fact to a customer.

17. **Does Anthropic's default cache TTL still ship at 5 minutes, or did it change from a 1-hour default sometime around March 2026**, as one unverified third-party source claims? Could not be independently confirmed against a changelog.

18. **What is the real, current numeric cap on AWS EDP/PPA Marketplace drawdown, and does it apply per-vendor or across all Marketplace SaaS spend combined?** AWS's own buyer FAQ confirms the mechanism exists but states no percentage; the "25%" figure circulating traces to a single blog.

19. **Does Google Cloud's Marketplace Channel Private Offer (MCPO) mechanism carry the same eligibility restrictions AWS applies to its EDP/PPA drawdown?** Single-sourced to one ISV guide, never checked against Google's own docs.

20. **Is there any documented, provider-agnostic measurement of hosted-API T=0 reproducibility rates for Claude and Gemini specifically** — not just the well-studied GPT-3.5/4 cases? Every concrete empirical non-determinism number found in this sweep (the 152334H blog, the ACM TOSEM study) is OpenAI-specific. No equivalent measurement exists for Anthropic or Google.
